# Database / Domain Business Rules

1. Stock is derived from inventory movements or a clearly defined stock ledger; avoid silent direct mutation.
2. A cart is not an order.
3. A paid/confirmed order must preserve the price and product name shown at purchase time.
4. Inventory reservation and deduction must be protected from concurrent overselling.
5. Custom print requests do not become production jobs until they pass the quote/approval step.
6. Every inventory adjustment needs a reason and actor.
7. Never delete financial/order history casually; prefer status changes or archival semantics.
8. Deposit policy: Deposits (`DEPOSIT_PAID`) are optional, required for orders with total value >= 300,000 VND. Orders under 300,000 VND may proceed without deposit unless requested by sales agent.
9. `MADE_TO_ORDER` products do not require finished goods inventory to be checked or reserved at checkout. Material consumption occurs upon production job start.
10. Cancelling an order that has already consumed finished goods (`SALE_OUT` at `PRODUCING`/`READY_TO_SHIP`) must automatically record an immutable `RETURN_IN` movement to restock.
11. Raw material movements during print job start must serialize under a `materials` table row lock to prevent negative raw material balances.
12. Customer 3D design files are strictly private; storage paths are referenced in DB and accessed only via short-lived authenticated signed URLs.
13. Workflow status transitions must follow strict directed graphs; unauthorized status jumps or backward transitions are forbidden for regular operations.
14. Public order tracking must mask sensitive PII (name, phone, detailed address) and require secondary verification (e.g. phone suffix).
15. Phase 12 — a print job consumes exactly one physical filament spool (`print_jobs.spool_id`); no multi-spool/AMS support. Spool consumption must lock the specific `filament_spools` row (`FOR UPDATE`) before checking `used_weight_grams + consumed <= initial_weight_grams` and inserting the `material_movements` row — never let two concurrent jobs (or a job racing a stock-count adjustment) push a spool's `used_weight_grams` past its `initial_weight_grams`.
16. Phase 12 — `filament_spools.status` only carries 2 manually-set values (`ACTIVE`, `ARCHIVED`); the 4-tier low-stock warning shown in the Admin UI is always computed at query/render time from `(initial_weight_grams - used_weight_grams) / initial_weight_grams`, never stored, so it can never drift out of sync with the weight columns.
17. Phase 12 — `expenses` (workshop expense tracking) is 100% OWNER-only; `deleteExpense` is a soft-cancel (`status = 'CANCELLED'`), never a real `DELETE`, per rule #7 above.
18. Phase 13 — public quote access (`/quotes/[quoteNumber]`) follows the same dual-verification/masking contract as rule #14: a valid, unexpired HMAC token grants full detail; without one (missing/expired token), the page must require a secondary factor (`phoneSuffix`, same as `getPublicOrderByNumber`) and mask customer PII (name, phone) — `quoteNumber` alone is never sufficient for either full or masked access. Internal cost fields (`pricing_breakdown`'s `machineDepreciationVnd`/`electricityCostVnd`/`failureBufferVnd`/`laborCostVnd`) must never be serialized to any public response; expose only a purpose-built public pricing DTO.
19. Phase 33 — VAT is versioned configuration (`pricing_configs.vat_enabled` / `vat_rate_bps`, default off). A Quote snapshots the VAT computed **server-side from the pricing config current at creation** (`vat_rate_bps`, `vat_amount`); the browser never sends VAT, and a client total that differs from the server total is rejected (`QUOTE_TOTAL_MISMATCH`). Turning VAT on or changing the rate never changes existing Quotes (ADR-0022) — staff re-create a DRAFT quote if it must carry VAT. VAT base (subtotal + shipping − discount) and half-up rounding are pending accountant confirmation (O2).
20. Phase 33 — one `/bao-gia` item (file + configuration + quantity) = one immutable Quote (`quotes.custom_request_item_id`); the DB guarantees the item belongs to the same request. Accepting a Quote auto-rejects only the still-open alternatives of the **same item** (or, for MakerWorld quotes, the same `sourceUrl`), never other items. Estimated prices on `/bao-gia` are never binding; the browser never submits a price — the server re-measures each stored file (within a 20MB budget) and prices it itself. Items whose numbers come only from the browser (`CLIENT_REPORTED`) are never pre-filled into a Quote without a server re-verification.
21. Phase 34 — every public checkout carries a client-generated UUID idempotency key. The same key may replay only the same canonical payload and must resolve to exactly one `orders` row; reusing it for a different payload is a conflict. Public reads of newly uploaded private attachments require an unexpired HMAC claim bound to the exact Storage path before any service-role access.
22. Phase 36 — order lifecycle side effects: cancelling an order also cancels its print jobs that have not started (`QUEUED`, `FAILED`, `REPRINT`); `PRINTING`/`QC` jobs are left for staff. A `CANCELLED` order may only move payment to `REFUNDED` and shipping to `RETURNED`; marking it paid/shipped needs an OWNER override with a reason. Order lines snapshot `product_type` at purchase and are immutable (the only allowed change is the FK's own `variant_id → NULL` when a variant is deleted).
23. Phase 36 — a manual stock-out can never take a warehouse's on-hand below zero, and `ADJUSTMENT_OUT`/`DAMAGE_OUT` can never push Available Stock (on-hand − reserved by `NEW`/`CONFIRMED` orders) below zero; staff cancel/adjust the reserving orders first. Material is booked once per real print attempt, and every entry into `PRINTING` books: even an OWNER override may enter `PRINTING` only from `QUEUED`/`REPRINT`/`FAILED`, and may move a job back to `QUEUED` only from `CANCELLED` when it never booked material (a printed job is re-run via `REPRINT`). A job's material/spool can only change while it is `QUEUED`/`FAILED`/`REPRINT`.
24. Phase 36 — financial/production history is never hard-deleted: a custom request with an `ACCEPTED` quote or a started print job (status past `QUEUED`, or any job that booked material — even if later `CANCELLED`) can only be `REJECTED` (DB triggers back this up). `pricing_configs` rows are never updated; a config that priced a quote/product can never be deleted. Quotes with no item and no MakerWorld link are revisions of the same request — at most one of them can be `ACCEPTED`. A `REJECTED` request cannot have a quote accepted.
25. Phase 36 — the public phone-suffix check (rules #14/#18) allows at most 10 wrong answers per order/quote per 24h regardless of IP; correct answers don't count. "Today"/"this month" in every report means the Asia/Ho_Chi_Minh calendar.
26. Phase 37 — public marketing claims shown in brand images (home banner, social cover): "Nhận in từ 1 sản phẩm", "Freeship đơn từ 299k", "Ship toàn quốc" (OWNER confirmed 2026-10-20). These are display-only messages: checkout does **not** yet compute free shipping, so `shipping_fee` stays whatever staff/pricing sets. Implementing a free-shipping threshold needs its own phase (money as integer VND, snapshot on the order per rule #3) — and the banner must be updated if the policy changes.
27. Phase 40 — multi-color prints cost the filament purged during AMS color changes plus the machine time of those changes. A sliced `.3mf` includes both in its instant price. For an unsliced multi-color project the instant price is a **single-color floor** ("Từ ~X đ") and the estimated purge/changes are shown as quantities, explicitly "chưa có trong giá" (ADR-0043 §6) — never a lower number presented as the full price. Estimates are rounded UP to 5.000đ and are never binding; the official price comes from staff (who slice the file) — the shop does not slice customer files automatically.
